# Freestock yield account

Per-user contract for a USDG lending account. New V2 deployments have no Freestock deposit cap. No shared Freestock account or factory is configured; each user deploys their own account from their wallet. Owner-only deposits, withdrawals, compounding and stock purchases. No operator or background spending authority. The owner's wallet must approve every transaction.

The vault, asset, router and deposit-cap field are immutable constructor inputs. The canonical V2 deployment uses `MaxUint256`, so there is no Freestock business cap. Archived V1 deployments retain their 100 USDG principal-based deposit limit; they are not upgradeable. The stock allowlist is constructor-only storage with no setter. The production client must additionally verify the chain and all exact addresses. The contract tracks principal separately from current vault value; losses must recover before available gains can be spent. Owner withdrawals reduce principal, and a full exit clears it. Explicit compounding increases the principal baseline; underlying vault returns already accumulate while shares are held.

Harvest accepts typed basket swaps, approves only the selected amount to the fixed router, checks actual token receipts, resets allowances, enforces a short deadline and rechecks principal coverage before and after the swaps. The entire harvest reverts on any failed basket leg. Direct token or vault-share donations increase account value and are included in available gains; they are not distinguished from lending income. No principal, liquidity, return or stock-price guarantee is provided.

Real automation requires a separately designed permission model. This contract deliberately has no keeper authorization. The archived V1 source passed 39 assertions on a local fork at block 58051564. Full vault-to-NVIDIA conversion, rollback, ownership, approvals and exit evidence are in `test/`. Test time was accelerated 30 days, and funds were fake. These results are not return forecasts or mainnet deployment.

Compiler: Solidity 0.8.30, optimizer 200, viaIR true, Cancun. `artifacts/account-standard-input.json` contains exact compiler input and `FreestockYieldAccount.artifact.json` contains ABI, bytecode and immutable offsets. The artifact records a source hash; the application verifies creation calldata, canonical deployment receipt, runtime bytecode and fixed configuration getters. Mainnet activation requires a fresh actual-sender simulation and verified deployment/receipt handling; the live application prepares, simulates and validates wallet-approved deployment, exact approval, deposit, reserve/compound, five-stock harvest and full withdrawal. Its receipts are checked against canonical chain state. Mainnet account creation is performed only by the participant, not by the builder.

See the [contract reference](../docs/CONTRACTS.md) for every configured dependency and enabled token address, public explorer links, function and event documentation, and the difference between contract capabilities and the primary interface. The [backend guide](../docs/BACKEND.md) explains verification, unsigned preparation and receipt handling.

V1 source, artifact, exact compiler input and frozen deployment configuration are retained in [`legacy/v1/`](legacy/v1/). Both V1 and V2 deployment/runtime identities are verified before an existing account can be used. Recompile the current V2 artifact with `node scripts/compile-account.mjs` from the repository root.

## Current V2 regression evidence

The [V2 and archived V1 local-fork regression](test/V2-V1-FORK-REGRESSION.md) passed 59 assertions: a 1,000 USDG V2 deposit, exact allowances, owner restrictions, a constructed-surplus NVIDIA conversion, both full exits, and the original V1 cap. All transactions used generated test wallets and fake funds on a local fork. This is not a public funded deployment or measured lending-income result.
